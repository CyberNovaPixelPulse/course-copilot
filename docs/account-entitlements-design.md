# 帳號額度 module 設計共識

狀態：Q1–Q21 已逐項確認並發布為 GitHub Issue #1；對應本機實作已加入。尚未遷移、部署或驗證正式資料。

## 目標與 module 責任

以小而明確的 interface 集中授予、查詢、保留、扣除、釋放及匯出資格，並保證成功辨識結果保存與正式扣次的一致性。提高 depth、locality 與 leverage，讓各呼叫端不再自行拼接對帳與扣次順序。辨識規則、付款真偽驗證及畫面呈現維持各自責任；使用現有 Turso 與記憶體 libSQL adapter。

## 已確認的行為

- 帳號資料庫紀錄是所有權益的最終依據；跨裝置一致，不同帳號隔離，舊瀏覽器憑證不能恢復已消耗額度。
- 匯出資格與辨識額度分開，已取得的匯出資格不因額度用完失效。
- 每帳號一次三次免費額度；可可靠還原舊用量則保留剩餘量，無法還原的舊帳號切換時一次性取得三次。
- 購買或兌換後保留並優先使用剩餘免費次數。此項為明確同意的方案調整；其餘價格與方案保留。
- ECPay、Stripe 每筆有效付款增加三十次，同筆只入帳一次；付款通知、返回確認及後續核對共用此保障，不依賴返回成功頁。
- 同帳號同碼只兌換一次；全域名額、帳號兌換紀錄及授予一起成功或失敗，重試回傳原結果。
- 辨識前保留一次額度，期限初始為三分鐘；明確失敗立即釋放。至少一筆可用課程與必要紀錄保存完成後才正式扣次；失敗成本由產品吸收。
- 成功與逾期釋放只能一方生效，逾期舊工作不得再扣次或宣告成功。同次送出重試沿用工作身分；失敗或逾期後需明確重新送出才建立新工作。
- 成功課程結果自完成保存七天，只供原帳號取回，不額外保存圖片，不同步後續編輯。到期刪除課程內容，必要扣次與防重複紀錄另行保留。
- 上傳區最近辨識列出七天內工作與可取回結果；使用者主動恢復，不覆蓋正在編輯的課表，不自動重新辨識。
- 資料庫不可用時暫停需要權益驗證的操作；已載入課表仍可編輯。付款尚未入帳顯示確認中，不誤報額度不足或要求重付。
- 移除用量 POST 獨立增加計數的能力，正式扣次只來自成功辨識。
- 舊權益依可信證據恢復，不能確認則保存待核對。提供登入後核對請求與管理者受控補登工具，記錄理由、防重複，不建立完整管理後台。

## 必須通過的驗收情境

1. 同帳號跨裝置取得一致餘額；切換帳號、清除儲存、舊憑證重播不轉移或重領權益。
2. 免費剩兩次再購買三十次，共三十二次；先使用免費次數，免費本身不授予匯出資格。
3. 剩八次再購買一次為三十八次；同筆付款重複通知、並行確認不重複入帳；付款後未返回網站仍可入帳。
4. 優惠碼最後一個名額並行兌換只有一人成功；入帳失敗不吃掉名額，同帳號重試不重領。
5. 最後一次額度並行送出只有一個工作獲准；無課程、模型失敗、必要紀錄失敗不扣次。
6. 成功保存結果與正式扣次一致；回應遺失後重試可取回且不再次扣次。完成與逾期競爭時僅一個狀態成立。
7. 關閉頁面後成功結果仍可由原帳號取回；七天後課程內容不可取回，其他帳號永遠無法取回。
8. 資料庫故障、付款確認中、額度不足及工作執行中有不同提示；舊憑證不能繞過故障時的權益驗證。
9. 舊權益核對補登可追查且不能重複授予；用量查詢與舊扣次入口不能自行改變正式用量。
