# 帳號權益切換與核對

本機實作不代表正式環境已啟用、已遷移或已驗收。不要在舊版與新版同時處理辨識扣次時執行切換：舊用量寫入不會反映到新版工作帳本。

## 切換前

1. 備份資料庫與既有設定，先在隔離的資料庫驗證。
2. 以 `node --env-file=.env.local scripts/account-admin.cjs audit` 執行只讀盤點。此模式不建立資料表、不授予額度；輸出包含帳號與核對證據，應當作管理資料保存。
3. 核對 ECPay 已付款訂單與既有用量。新流程僅以已付款訂單數乘三十，扣除持久保存的舊 ECPay 用量；不把下單時的舊權益快照當作優惠碼或 Stripe 證據。此保守策略可能需要人工補登混合來源帳號的差額，盤點時需標記。
4. 舊優惠碼與 Stripe 缺乏本機完整個別帳號歷史，不從舊憑證自動授予。核對 Stripe 供應者端訂單及帳號資訊、已消耗量，再由核對流程補登；無法確認餘額時不承諾自動還原。新 Stripe checkout 有持久金額／幣別／帳號紀錄，舊 checkout 的確認會轉待核對。
5. 免費用量無可靠帳號證據的舊帳號只在首次建立帳號權益時取得三次；若盤點找到可靠歷史免費用量，需在正式切換前以經審核的帳號初始化資料還原，不能以舊憑證作證。不得在已開始新辨識後覆寫餘額。
6. 設定 Stripe 付款通知簽章密鑰 `STRIPE_WEBHOOK_SECRET`；通知網址 `/api/webhooks/stripe`，接收 `checkout.session.completed` 與 `checkout.session.async_payment_succeeded`。只有先通過本機 checkout 帳號、金額、幣別核對的 paid 付款可授予。未知 checkout 回傳 503 供重試或管理者核對。
7. 設定 `CRON_SECRET`，由排程以 `Authorization: Bearer <CRON_SECRET>` 呼叫 `/api/internal/cleanup`，或使用受控環境執行 `cleanup --apply`。至少每日執行；結果滿七天立即不可取回，實體內容於清理時刪除。日常帳號操作也執行清理。若要求實體七天到時即刪，需配置相應更密集排程與監控。
8. 在測試資料庫重跑並行、回滾、重播及使用流程驗收，再安排短暫停止辨識與舊扣次的正式切換窗口。通知失敗應由供應者重試；切換後核對漏單，不能要求使用者重新付款。

## 受控操作

- `audit`：只讀列出 ECPay 來源與待核對請求。
- `import-ecpay ACCOUNT --apply`：將該帳號可驗證的 ECPay 訂單／用量一次匯入，重跑不重授予。登入權益查詢同樣會同步其新訂單。
- `resolve REVIEW_ID CREDITS true|false "核對依據與管理者身分" VERIFIED_SOURCE --apply`：完成核對並授予指定額度及可選匯出資格。必須填理由，不把用戶提交的說明或有效舊 token 本身當作已驗證證據。同一請求重跑不重複授予；VERIFIED_SOURCE 必須是獨立可驗證的付款／兌換來源身分，不同請求重複同來源亦不重授予。
- `initialize-free ACCOUNT REMAINING EVIDENCE_ID --apply`：僅在帳號尚未初始化前還原可靠的免費剩餘量（0–3），同證據重跑不重授予；正式切換前執行，拒絕覆寫使用中的帳號。
- `cleanup --apply`：釋放已到期保留並刪除滿七天的結果內容，保留防重複及扣次紀錄。

補登前須按付款編號／既有補登紀錄核對來源，跨請求使用相同 VERIFIED_SOURCE；不得任意建立新來源以重授予同筆付款。正式補登只提供給具有資料庫權限的管理者，站內沒有管理者授予入口。

## 驗證限制

記憶體 libSQL 測試驗證本機交易語義，不等同已驗證正式 Turso 的並行、部署時限、排程、通知設定或實際付款。實作合併前應檢視測試結果，正式切換另需執行上述驗收及獨立授權。

## 辨識記錄的來源欄位

新工作記錄以額度保留實際選定的 `credit_bucket`（`free` 或 `credits`）為準。免費記為 `payment_type=free`，混合來源帳號額度記為 `account_credit`，不再依匯出資格猜測為付費／優惠碼；辨識不代表當次收款，`fee_charged_twd=0`，未能單獨歸因的優惠碼欄位為空。收入及優惠碼授予應查其授予／兌換紀錄。
