# 課表辨識實作與驗收

工程子議題 #3–#8 已完成。2026-10-27 使用者在十三次真圖呼叫證據後接受目前效果，要求 #9、#2 完成關票；已知星期錯置與真圖案例覆蓋不足仍保留。詳見 experiments/schedule-recognition/results/acceptance-closeout.md。未部署、未更動產品資料，提示及驗收紀錄尚未推送。

## Interface 與責任

課表辨識 module 接收圖片內容與既有帳號／工作身分、額度來源，交付可編輯課程或安全的 RecognitionError。正式模型與固定回應 adapter 經過相同的完整回應驗證、正規化、時段整理及必要記錄。

請求入口仍處理登入、檔案類型／大小、工作保留、重試、結果保存與正式扣次。它不再整理節次，也不重新記錄辨識錯誤；同一工作重試不另呼叫模型。頁面關閉不主動取消已被伺服器接受的工作，以沿用帳號工作恢復政策。

模型階段最長等待 45 秒，SDK 不自動重試；必要記錄最長等待 15 秒。模型逾時會傳遞取消訊號；即使 adapter 未遵守訊號，也不會在等待期限後再次回報成功。記錄等待逾時不保證底層資料庫寫入已取消，帳號工作終態仍是結果保存及扣次的最終依據。

## 記錄相容性

新記錄使用 cc_recognition_logs，以帳號與工作組合作識別，模型用量欄位允許空值。模型是否回應與整理是否成功分開保存（normalization_status 不代表工作已完成）；未知用量不記為零，不持久保存圖片、模型完整回應或任意原始錯誤。

用量兩欄皆已知時，在同一寫入批次保存新記錄並寫入原有 ai_logs，維持數字欄位與既有 task_id、step、stage、payment_type、fee_charged_twd、coupon_code、events_count 等中繼欄位。模型回應但整理失敗時，舊記錄 status 表達模型回應，新記錄及 normalization_status 中繼欄位表達整理失敗，不將二者混為一談。

用量未完全取得時，只寫可表達未知的新記錄，避免既有數字型消費者把零當成真實用量；如需完整故障率及未知用量統計，讀取新記錄，而不是假設 ai_logs 包含全部辨識嘗試。舊欄位的 task_id 現對應穩定的工作識別，並新增 account_id、job_id、normalization_status 與 failure_code。收入及優惠碼歸因仍應查授予紀錄，不從匯出資格猜測。

必要記錄失敗時回報 logging_failed、工作不扣次。若底層逾時寫入稍後完成，記錄描述當時模型及整理結果，不能取代帳號工作終態；不要僅以整理成功推論正式扣次已完成。

## 驗收邊界

固定回應覆蓋正常與異常欄位、未知節次、教室保留、合併及衝突、模型失敗與記錄失敗。真實 libSQL 測試確認未知用量與舊數字型表相容、不同帳號可使用相同工作識別。帳號入口整合確認失敗釋放、成功可恢復、重試不重複辨識及額度耗盡仍可匯出。

已核准範圍的真實圖片實測及使用者品質判斷已完成，本輪以已知限制接受結案，見 experiments/schedule-recognition/README.md。其餘代表性真圖案例未補齊；工程測試及使用者結案決定均不能作為整張零差異或正式環境已通過的證據。
